# 测试桥加载竞争修复（0.2.1）

用户报告 Stagehand 已启用时再启用桥会报错，重开 Stagehand 后成功。实际日志中的加载异常是 `System.IO.IOException`：桥的 `WriteStatus()` 在构造函数中写 `status.json.tmp` 时，文件被另一写入占用。旧代码先订阅 framework Update，随后由构造线程写状态；框架线程可能同时进入同一路径。这是本次可证实的桥初始化缺陷，日志没有显示 Stagehand IPC 版本或连接失败。

修复将首次状态发布移到订阅之前，并最后注册 framework 回调；构造、执行、更新和释放以实例锁串行化。状态文件改为独立临时名和原子替换，短暂 IO/权限占用返回待重试状态，不再使构造或清理失败。失败的构造撤销已添加的订阅；持久 Stage 恢复移到 framework 线程处理，延迟回调先检查实例是否已释放。

旧版本失败构造可能已留下回调，不能假设 Dalamud 能取回未构造完成的对象并调用 Dispose。新桥使用 `control-v2` 子目录作为命令/状态/事件通道，旧实例无法消费新请求。原配置中的 OwnedStages 所有权清单保留。旧失败回调的内存存活不在本次热载中枚举；正常重启会结束旧进程，本次无需为此重启游戏。

Release 编译零警告，31 项检查通过，包括旧固定临时文件被锁、构造/回调并发发布、目标文件占用后重试、不同实例临时文件隔离。热更新工具拒绝仍加载的桥，备份旧完整包，支持写入失败回滚；模拟已验证。

用户仅禁用测试桥、保持 Stagehand 和游戏运行后，热更新到 0.2.1。用户确认重新启用无报错，日志确认加载成功，新协议状态确认实际版本 0.2.1、同一游戏进程；随后四态 probe 完成，实际 IPC revision 1.2。无需反复关闭 Stagehand。

为支持后续热载，原登记目录现作为部署副本使用；旧 0.2.0 完整包在热更新前另存冻结备份，新 0.2.1 构建包单独保留。`tools/deploy_stagehand_bridge_hot.py` 不写 Dalamud 配置或游戏 DLL，注册路径不变。原生采集 add-on 和 r10 基线均不变。此修复属于加载正确性；性能工作仍按用户要求暂缓。
