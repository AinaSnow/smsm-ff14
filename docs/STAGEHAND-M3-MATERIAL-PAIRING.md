# M3 准备：确认当前角色材质取样

对 M2 已有 OFF/WARM/COOL 原始采集逐文件验证后，分别查看绘制前后 RGB 变化区域。三帧中的掩码均覆盖当前角色的裙装/上衣，绘制元素数为 7914，原始 PS 为 `e86f0d4916054deb`。对应绘制序号分别是 4、1、4；固定序号不能稳定代表这件衣服。匹配使用相同 VS、元素数、非零 RGB 贡献及人工查看空间掩码，不把这些字段推广为其他角色的身份。

`tools/compare_stagehand_material.py` 核对完整性、原始 shader、格式、viewport 和唯一非零候选，交集掩码再向内收缩三像素，减少轮廓轻微动作的干扰。18,147 个共同内部像素的 RGBA16_FLOAT 材质输出均值如下；数值属于游戏材质编码域，不是屏幕亮度百分比，也不能直接当线性能量。原指令在输出前有非负钳制、平方根和缩放；早期 `mean_linear_rgb` 字段名不构成线性输出的证据。

| 状态 | R | G | B |
|---|---:|---:|---:|
| OFF | 0.24045 | 0.22986 | 0.23488 |
| 暖光 | 0.77642 | 0.50580 | 0.36767 |
| 冷光 | 0.33839 | 0.50768 | 0.91510 |

暖光提高红色贡献，冷光提高蓝色贡献，与用户看到的变化方向一致。这给出了当前裙装材质输出随预设变化的证据。帧间仍有角色动画和游戏光照变化；仅三帧没有重复 OFF 对照，不能把全部差值当作该灯的精确贡献。

现有 output audit 记录绘制状态和渲染目标，没有同时保存该绘制的完整 CB/SRV 输入。因此本轮尚未定位原生灯参数对应的 GPU 缓冲、筛选规则或光照纹理，M3 尚未通过。下一步先按已确认的材质和有颜色输出的阶段定点采集输入，保存绑定范围与资源身份；采用重复 OFF/暖/冷对照，再检验参数变化是否稳定解释材质输出。头发、皮肤和地图原有灯分别需要自己的证据。

原始帧、位置、UI、资源指纹及可视化掩码只保存在本地忽略目录。这里仅提交分析工具和汇总结果。r8 保持关闭。
