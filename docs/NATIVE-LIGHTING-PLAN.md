# 原生场景光照改进与 ReShade 插件验证计划

日期：2026-10-08。状态：M0 工程准备、M1 诊断实现与真实快照已取得；r2 的 BGRA8 单帧实机读回复核完成。M2 部分审计判断为“需要补充接口”，位置/法线生产者、独立坐标、对象/局部灯和成本验收仍缺证据，未进入画质迁移。进度见 [NATIVE-DIAGNOSTIC.md](NATIVE-DIAGNOSTIC.md)，路线判断见 [NATIVE-LIGHTING-AUDIT.md](NATIVE-LIGHTING-AUDIT.md)。

2026-10-09 更新：已定位历史位置生产者的深度重建链，实际原始 PS 回放通过；排除将位置/深度回环当独立证据的推断。r3 生产者元数据候选及离线/回调/升级验证完成，当前帧核对待进行，见 [NATIVE-PRODUCERS.md](NATIVE-PRODUCERS.md)。

本计划按用户最新目标调整后续优先级。当前仓库基线为 `ead6d5e`，已研究的客户端为 `2026.09.15.0000.0000`；进入实机前重新确认版本。本次只记录计划，不改变游戏、DLL、现有实验包或默认效果。

## 1. 目标与方向调整

目标是让日常游戏中的人物和环境更自然地响应原有光照，参考 VRCLightVolumes 的空间受光效果：

- 角色经过明暗或冷暖交界时，身体不同部位随各自位置和朝向受光，变化连续。
- 窗边、室内外、局部灯具附近保留有方向的明暗层次；不通过统一提亮暗部或全局染色制造效果。
- 游戏原有动态灯光发生变化时，材质响应正确跟随。
- 优先保持肤色、白衣、衣物褶皱自然，再覆盖其他材质。

用户所指的“动态”同时包含角色在空间光场内移动，以及光源自身变化。参考 VRCLightVolumes 的视觉与数据组织思路，不预先承诺直接移植、完整实时 GI 或全地图自动支持。

自定义单灯降为辅助验证和后续摄影实验，不再阻塞主线。已有柔和漫反射实现只作用于新增灯的贡献，不能算已完成原版漫反射改进。漫反射过渡、投影阴影软化、环境间接光分别验收。

## 2. 已有成果与核心未知项

| 内容 | 可复用成果 | 尚不能据此证明 |
|---|---|---|
| 材质路径 | 已定位全屏 `415a922293923fa4` 与网格 `980154264a89fba1`，已有位置/法线接口审计及原版 PS 离线对照 | 所有角色、头发、透明材质均被覆盖 |
| 光照算法 | 单灯、柔和漫反射、屏幕空间遮挡已有实际 WARP 绘制验证 | 游戏原生光源与场景探针已接入 |
| 验证工具 | 浮点读回、差分、重投影和错误输入检查 | 合成数据通过等于实机正确 |
| 包管理 | 不可变包、独立开关、备份、回退流程 | 能直接用于 ReShade 插件部署 |
| 环境光研究 | 已知原版材质存在环境光合成输入 | 输入一定包含可重新采样的三维空间光场 |

本轮首先回答：

1. 人物当前的环境光按对象、顶点还是像素求值？取样是否随表面位置变化？
2. 是否存在可复用的空间探针、方向光照、区域索引或插值数据？
3. 原生局部灯的参数、筛选与更新发生在哪里，如何影响人物？
4. ReShade 插件能否在正确阶段稳定取得这些数据，且成本可接受？

不能预设原版只给整个人统一亮度，也不能由字段名、资源指针、绑定存在推断具体功能。需要静态数据流与实机变化互相印证。

## 3. 架构选择

候选方向为 **ReShade + 专用 C++ Add-on + 按需材质 shader 修改**。

普通 ReShade FX 适合效果原型、调参和后期，但标准颜色/深度输入不会自动提供原生灯光、探针、完整材质和世界空间数据。迁移的理由应是更方便的渲染事件跟踪、资源生命周期管理和运行时控制。

Add-on API 提供数值视口事件和资源操作能力，官方也有 shader 替换、资源检查及帧内效果执行示例。接口存在尚不等于 FF14 的目标数据已能可靠取得；插件版本、实际回调覆盖、初始状态、延迟上下文与资源重建必须验证。

沿用现有研究数据与测试，不立即重写全部 shader。3DMigoto 与 ReShade 的 shader 标识不能直接混用；记录原始 DXBC 摘要并建立经过核对的映射。

## 4. 阶段与交付

### M0：冻结最小验证范围

交付：一页目标资源表与测试环境清单。

- 固定 ReShade 版本、Add-on API 版本、源码提交和编译配置。
- 记录游戏版本、分辨率、缩放/抗锯齿、SDR/HDR、现有注入组件及基线文件摘要。已知用户使用 SDR，进入测试时复核。
- 选定上述两条材质路径为观察入口，必要时沿其输入向前追踪生产者。
- 设计停机安装、备份与完整恢复步骤；先在模拟目录验证文件操作。

验收：资源观察范围明确，已有客户端文件所有权及恢复路径明确。此阶段不要求完善通用工具平台。

### M1：只读 ReShade 诊断插件——首个工程交付

交付：插件源码、可复现构建、默认关闭的诊断候选包、采集清单和日志格式。

“只读”指不替换游戏 shader、不修改其光照输入；仅跟踪状态，并复制选定数据到插件自己的读回资源。

- 识别目标绘制，记录实际视口数值、shader 身份、相机/环境光候选缓冲区和相关纹理绑定。
- 记录资源尺寸、格式、子资源、阶段、绘制序号、来源帧、相机候选矩阵及写入/更新证据。
- 区分已确认的语义、候选语义和未知内容；无法关联的资源保留为未知。
- 默认不抓帧；每次手动触发只采下一帧，每个目标最多一次绘制。
- 首版选定原始资源数据合计预算为 256 MiB。先根据描述估算，超过预算则停止并报告，不静默降精度或扩展为全帧导出。预算不是总显存或总进程内存承诺。
- 优先限制 GPU→CPU 同步；插件空闲成本和触发采集时的停顿分别记录。

验收：实际记录数值视口和至少一条目标路径的同阶段相机/资源快照；重复触发不混用旧资源，缺失和预算超限可明确识别。编译成功不算完成。

### M2：一次小范围实机数据审计——迁移决策点

交付：数据来源与语义报告、已知缺口、实测成本、迁移结论。

使用一个有明暗或冷暖交界的固定场景。先保持原版渲染，依次观察：

| 操作 | 要区分的问题 | 判据 |
|---|---|---|
| 镜头尽量固定，角色穿过交界 | 光照是否随角色/表面世界位置变化 | 数据与空间位置变化对应，不能仅靠最终截图猜测 |
| 角色固定，转动镜头 | 相机相关量与世界光场的区别 | 正确转换后世界参考一致；未知项明确标注 |
| 固定观察一个已确认的原生局部灯变化 | 哪些参数是真正的灯光输入 | 参数、执行路径及受光变化相互对应 |
| 完成一次场景切换 | 资源是否被销毁、重建或复用 | 没有沿用旧场景资源；找不到目标时停止读取 |

若所选发光物没有实际照亮材质，记录其为无效灯光测试对象，不要求用户重复寻找肉眼差异。

原始证据保持无损。位置、深度和法线只有在映射关系及写入历史成立时才能合用；同一指针不是内容相同的证明。相机逆矩阵往返也不能代替独立位置/像素/深度对应检查。

成本分开测量：原基线、插件加载但未采集、触发一次采集。记录测试时长、帧时间分布和峰值停顿，不把 WARP 数值或采集停顿当正式效果的 GPU 开销。

M2 必须给出以下一种结论：

- **值得迁移**：关键数据可稳定取得，资源状态可追踪，已有具体材质接入方案。
- **需要补充接口**：列出缺的字段/阶段和一个有边界的补证任务，不继续扩大通用框架。
- **当前路线不足**：只有最终颜色/深度，或缺少可复用的空间信息；说明可做的近似及限制，不宣称已实现光照体积。

### M3：原版光照下的最小画质对照

进入条件：M2 已确定真实输入及可验证接入位置。

交付：一个独立开关、一个固定场景、原版/候选配对截图或短视频和成本记录。

- 根据证据选择一个问题：空间采样/插值、方向环境光求值，或原生局部灯的材质响应。一次只改一项。
- 保留原版光照作为回退；先确认是否替换原有贡献，避免将同一份环境光重复叠加。
- 优先人物肤色与白衣，检查局部明暗、色相、高光与纹理细节。镜面项、曝光、Bloom 与漫反射分开观察。
- 角色移动时变化连续，镜头运动不制造错误跟随；关闭后恢复基线。
- 自定义补光灯关闭。若真实输入不支持空间细节，不能用一条全局曲线声称完成空间光照。

### M4：扩展与后续研究

在 M3 展示明确收益后，再增加昼夜/天气、更多材质和地图、透明对象、多个原生灯的组合，以及性能优化。

若需要自建光照体积，另立可行性任务：明确场景几何与灯光数据来源、烘焙或运行时生成方式、世界坐标、遮挡、区域混合、加载/卸载及显存预算。一个手工布置的小体积只算局部原型，不等于全地图支持。预烘焙数据也不能直接保证适应所有天气、时间和动态遮挡。

自定义多灯摄影预设、SSGI 和完整硬件光追排在上述验证之后。景深/反射研究与既有实验保留，不因为差异小删除，但不占用当前主线的前置交付。

## 5. 现有效果迁移与保留

现有效果纳入迁移清单，分批适配并逐项验收，不因为更换框架而静默删除。M1–M2 先验证数据通路，不改变日常效果；确认值得迁移后，先恢复已接受的日常基线，再逐步适配实验功能。完成全部旧实验的迁移不作为 M3 原生光照研究的前置条件。

当前 `r10-managed` 的 `daily` 配置只启用 tone；不能把仓库中存在的所有实验都算作当前日常已启用功能。

| 内容 | 迁移处理 | 验收要求 |
|---|---|---|
| 已接受的色调方案 | 优先适配，保存原参数、公式及注入阶段 | 同场景对照白衣、肤色、暗部与高光；关闭后恢复原版，不改变 UI 或意外影响 Bloom |
| 原版 Bloom 与原版景深 | 保留游戏自身效果，不用新增后期效果代替 | 灯具光晕、景深开关及焦点行为与原基线一致 |
| 反射、阴影相关补丁、抖动、径向模糊 | 保留实现与证据，逐项适配；实验默认关闭 | 分别证明执行、实际输出变化和成本；反射还需检查边缘、过滤及运动稳定性 |
| 实验景深 | 保留近远层与合成研究，作为独立实验适配 | 不将已有离线合成验证写成完整散景完成；继续检查焦点过渡和边缘漏色 |
| 自定义单灯、柔和漫反射、遮挡 | 复用数学实现和离线测试，按需重接输入与资源 | 与原生光照主线分开，默认关闭；离线正确不等于实机覆盖 |
| 紫色执行标记等诊断输出 | 仅作为开发诊断选项 | 日常配置不得启用；标记可见只证明目标路径执行 |

迁移不等于把所有内容转成 `.fx`。材质阶段修改可通过专用 Add-on 适配；3DMigoto 的绑定、hash、命令列表和资源管理需要重新核对。色调若改在最终画面阶段执行，可能改变与 Bloom、曝光、UI 的关系，不能仅以截图相似或 LUT 近似视为等价迁移。r5 未验证方案不进入迁移基线。

每项记录原包与源码摘要、执行阶段、参数和默认状态、已知限制、候选实现、对照证据及回退方法。出现接口限制时明确标注“未迁移/近似/待验证”，不宣称已完整保留，也不预先承诺性能提升。

切换日常默认环境前，必须完成日常基线的实机对照、开关恢复和帧时间检查。旧的不可变包继续保留用于回退；试验新环境不覆盖旧包。

## 6. 测试与进度约束

- 每轮交付一个可见功能、消除一个已命名的数据缺口，或解决一个实机问题；不以测试条目数量代表效果完成度。
- 离线检查用于验证新逻辑及防止回归；未改动且已通过的模块不重复扩大测试。
- 新渲染逻辑必须有实际绘制和差分证据；编译、创建 shader、标记执行、画质收益和性能成本分别报告。
- 每轮结束写清“完成/未完成/下一阻碍”；M1–M2 若仍不能定位输入，先做路线判断，不无限追加采集工具。
- 用户测试合并为少量步骤。诊断包准备并验证后，再安排一次短实机配合；不提前要求反复 F8/F10 或安装未完成配置。

## 7. 部署与回退边界

- 保留不可变包、SHA 清单、独立开关和默认关闭原则。
- 不在游戏运行中替换注入 DLL；迁移测试采用明确的停机切换和备份方案。
- 先单独验证候选运行环境，再研究与现有组件共存；不假定两种注入器可以直接叠加。
- 不复用 r5 未验证的动态参数方案。新插件参数通道单独验证。
- 历史约束为本地开发、不推送或发布、不使用子代理。用户后续明确授权同步 Git、发布 r10、新分支开发并提交；本次按该授权执行推送与发布，继续不使用子代理。实机切换遵循上述停机及回退边界。
